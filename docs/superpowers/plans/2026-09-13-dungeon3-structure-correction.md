# Dungeon3 资源组合与地图逻辑修正

## 原图证据

资源规则由 `scripts/extract-dungeon3-rules.mjs` 从 Dungeon3.tmx 提取，裁剪不完整时直接报错。坐标均为 TMX 的原始格坐标，包含负坐标。

| 用途 | 原始图层 / 坐标 | 组合约束 |
| --- | --- | --- |
| 水波 | Water_details / (-17,-2)，4×2 | 使用 Water_detilazation（water_details_animation.png）的逐格动画，整组仅放在水格 |
| 墙段 | Walls2 / (6,15)，2×3 | 保留墙顶、墙面、墙脚三行，横向重复 |
| 墙内门 | Walls2 / (4,15)，2×3 | 门属于墙体；当前生成关闭的壁龛门，背后有碰撞墙；不占桥梁通路，不循环开关 |
| 地面机关 | Objects0 / (-22,7)，2×2 | 完整 plate_trap，按动画阶段启用伤害 |
| 喷火墙机关 | Objects1 / (-12,3)，2×6 | 保留龙头及全部火焰行；各格使用原始动画；只对正在显示火焰的格判伤害 |
| 平台立面 | Floor / (-11,9)，1×2 | 位于高台南缘，碰撞阻止直接跨越；楼梯处留开口 |
| 桥拱 | Floor3 / (-12,18)，6×2 | 完整拱面，仅在桥下有足够水域时放置 |
| 楼梯 | Floor / (-6,9)，5×3 | 不旋转透视资源；保留左右端帽和三行台阶，只重复中间列以适配通路 |

TMX 的图层覆盖顺序是 Water → 水下墙/水波 → Floor3 → Floor2 → Floor → Walls → Objects。图层名不是 Tiled 提供的可行走高度元数据；生成器需要另外建立高度和连接关系。当前采用从北向南 2、1、0 的台地高度，水平连接同高台地，垂直连接经楼梯下降一层。地板详情对应 Floor、Floor2、Floor3，墙体、台地边界、楼梯开口与碰撞使用同一份几何数据。

## 主题房间布局

房间不再把大型组合当作最后一步随机装饰。生成顺序固定为：房间拓扑与主题 → 主通路/安全通路 → 主题大型组合与成组机关 → 水域/铺装 → 少量散装装饰。房间外框仍遵守 3×3 槽位边界，避免为了容纳大物件直接扩大房间而让相邻房间粘连；主题使用独立的内部 `layout` 保留区决定 landmark、hazard lane 与 safe lane。

每层主题列表至少包含一间 shrine、crypt、gauntlet 和 flooded，额外房间才会复用 crypt/gallery。主题身份保持稳定，但主题内容密度由种子决定，随机只从不会堵塞安全通路的预留槽位中选择：

| 主题 | 实际生成组合 | 房间内位置与通路规则 |
| --- | --- | --- |
| 祭坛 shrine | 1 组完整 `Statue_fire` 5×5，共 25 个原始格；石板祭坛轴线随机为 64 / 96 / 128px | 火焰雕像完整放在房间北侧并与西侧边界保持实际玩家净空；中央保留 64px 安全通路，石板使用连接蒙版选边角/中心块，不重复某一个源角块 |
| 墓室 crypt | 每间随机 1–4 组完整 3×2 棺椁；中央 96px 石板墓道 | 四个候选墓葬槽位都经过通路校验，随机抽取其中 1–4 个；棺椁底座碰撞收窄并避开东西中心线，不会形成贯穿房间的碰撞墙 |
| 陷阱回廊 gauntlet | 随机 1–3 行连续 4×1 地刺；1 条 64px 绕行石板带 | 危险区始终位于回廊一侧，可从单排警示带变化到完整 4×3 地刺阵；另一侧持续保留安全通路 |
| 积水房 flooded | 固定两个南侧缺口，并随机增加 0–2 个北侧积水口，总计 2–4 个；64px 中央石板脊线 | 额外水口只从不碰中央 spine 的边缘槽位中选择；水面混用 ripple / foam / long / small 与 underwater ruin，密度也随种子轻量变化 |
| 展廊 gallery | 可为空，也可带 1 组完整棺椁及少量散装陈设 | 留白本身也是随机结果，避免所有房间都被装饰填满 |

所有主题铺装只描述连续区域，`dungeon3-renderer.js` 再根据相邻格关系选 `n/e/s/w`、四角和 `center`。这样石板区域不会再重复 `plates` 图集某一块角落而显示成零散圆点。

### 资源数量与位置口径

资源数量按“完整组合”计，而不是按屏幕上看见了几个 sprite 计：祭坛雕像始终是一组完整 5×5/25 格；每个 crypt 随机 1–4 组完整棺椁；gauntlet 随机 1–3 组 4×1 地刺。由于 4–9 房间图会额外生成 crypt/gallery，整层棺椁总数会随种子明显变化。水面组合数量依可用水格、组合尺寸和本层密度档位决定，不承诺固定总数。

位置使用房间相对坐标而不是世界固定坐标：地图种子决定主题落在哪个槽位，也决定该主题本次采用稀疏、中等还是密集组合；但 landmark/hazard/safe lane 的边界始终确定。随机性发生在“放多少、从哪些安全槽位选、细节有多密”，而不是发生在“完整组合能不能塞进去”或“玩家还能不能走通”。

## 已发现问题：主题安全区被后置散装装饰破坏

### Bug 现象

实机发现祭坛房内存在视觉上完全是地板的大片区域，但玩家无法进入。该问题并不是火焰雕像 5×5 组合本身画错，也不是单纯的 A* “孤岛”问题：针对所有已经被导航系统判定为可走的格做连通性回归时并没有复现断连；真正异常发生在更早一步——一些本应属于主题 `safeLane` 的视觉地面，在后置装饰阶段被新增碰撞体重新占用了。

### 根因

主题布局阶段已经为 shrine / crypt / gauntlet / flooded 等房间写入 `room.layout.safeLane`，但这个字段此前只是一份布局元数据。随后 `map-generator.js` 的通用散装装饰 pass 只避让主 `paths`、锚点、已有 solid、陷阱和其他装饰，没有把 `safeLane` 当成真正的布局保留区。因此“先规划安全通路、最后再随机塞装饰”在代码层面并没有闭环：随机的大/中型装饰仍可能把碰撞底座压进主题安全区。只要出生点、出口、房间中心等少数锚点仍能通过另一条路径互通，原来的 `validate()` 就会接受这张地图，所以这种局部大片不可走区域能够漏过生成校验。

### 处置方法

1. 通用装饰放置时读取当前房间的 `layout.safeLane`，任何装饰的完整视觉 footprint 与 safe lane 相交都直接放弃该候选位置；不仅阻挡型 decoration 避让，纯视觉 clutter 也避让，确保“这里能走”在画面上同样读得出来。
2. 保留原来的主路径、锚点、solid、trap 与装饰互斥规则；safe lane 是额外的主题布局约束，不替代全局连通性检查。
3. 增加专门的 walkability 回归：大量 seed / floor 完整生成后，按玩家真实碰撞半径采样各主题 `safeLane` 的可站立核心区域，要求不存在 `circleHitsSolid`。这个测试直接覆盖本次“视觉是空地但物理层不可走”的失效模式，而不是只检查 spawn → exit 是否存在某条路。
4. 仍保留全局锚点寻路校验。全局连通性回答“这一层能不能通关”，safe-lane 回归回答“主题明确承诺可以走的区域有没有被后续步骤悄悄占掉”；两者解决的是不同层级的问题。

### 这样处理的理由

不采用“继续缩小某一个雕像/棺椁碰撞框”的局部补丁，因为这次问题暴露的是生成阶段之间的契约丢失：主题 planner 已经决定哪里必须留空，但 loose dressing 不认识这个决定。继续逐个修素材只会让相同问题以后换成石堆、棺椁或新武器台再次出现。把 `safeLane` 变成后续生成步骤必须遵守的硬约束，才能让主题布局真正拥有自己的 footprint，同时仍保留房间外框、装饰随机密度和整体拓扑的随机性。

也不把“所有 floor tile 都必须可达”作为规则。靠墙地砖、雕像脚边和高台边缘可以因为角色半径而合法地不可站立；强行要求所有视觉 floor 都可达，会错误删除正常的贴墙装饰与地形。这里验证的是设计明确声明为安全通路的区域，因此约束既足够强，又不会把正常碰撞误判成 bug。

## 验证

- 原始 TMX 提取可重现，完整组合及资源帧索引校验。
- 多种种子验证门归属墙体、楼梯归属高度连接、机关避开重要锚点。
- 主题回归检查完整 5×5 火焰雕像、crypt 1–4 组棺椁、gauntlet 1–3 行地刺、flooded 2–4 个积水口及不同长度连续石板路径。
- 随机密度回归要求跨大量种子实际出现多个不同计数，而不是范围写了随机、运行结果仍固定。
- crypt 东西向连接按半径 26 单独回归，防止棺椁组合再次形成纵向碰撞墙。
- 主题 `safeLane` 在完整 loose-dressing 之后按真实玩家碰撞半径回归，防止视觉空地再次被后置碰撞体占用。
- 玩家及地面 Boss 使用真实移动碰撞器沿导航路径穿过桥和台阶。
- 大体型通路按半径 26 校验；地图格导航为 16，Boss 使用自己的碰撞半径，避免寻路与移动净空不一致。
- 浏览器确认水波、地面机关和喷火墙动画显示，检查控制台错误。

## 后续问题：主题挖水之后的机关与通路约束（2026-09-14）

在 `7ecd212` 基础上继续检查最终几何，发现三个阶段衔接问题：

1. **机关部分落在水里**：普通地板机关和墙壁喷火原本先于 `dressThemedRooms()` 放置。积水房后加的北侧水口会淹到火焰格，南侧缺口也与旧的地板机关固定位置相交。现在先完成所有主题水口，再由最终格子重建 `water` 碰撞矩形，最后寻找完整可用的机关位置。每组机关的危险区必须全在陆地，并避让主题安全通路、重要锚点和大型陈设；不通过裁掉机关格子来掩盖冲突。两侧水口都占用喷火朝向时，改用祭坛另一侧的有效墙面。
2. **非跨水连接也被标为桥**：相接的南北台地没有水隙，却仍然生成桥的范围。现在仅有实际水隙的连接生成桥对象；干地高差仍由对应楼梯和立面表达。
3. **单一动画时刻掩盖危险路线**：旧测试只在 1100ms 检查 `criticalPath`，有些错峰地刺当时恰好收回，而 150ms 时已经升起并覆盖该路径。现在生成器在验证用导航网格中排除所有危险格，证明各重要锚点之间存在不依赖机关时机的绕行路线；实际游戏的机关区域仍可进入。地刺阵从房间左侧第 1 格移到第 2 格，为西侧入口留下转入下方绕行区域的空间，不降低 1–3 排的变化范围。

### 生成结束时的校验

`layoutContractViolations()` 在通用散装装饰之后执行，检查声明的安全通路核心有没有实体或危险区侵入，以及机关危险格是否全部在最终陆地上。检查失败的地图不能作为生成结果返回。这样，`safeLane` 除了影响散装装饰选位，也成为生成器最后必须满足的条件。

沿用前一提交的通路取样口径：墙脚、高台边沿和角色半径允许造成的不可站立边缘不被误判；入口与出口的连接另外通过真实半径导航验证。新增回归覆盖最终水域与机关一致性、实际跨水桥元数据、多个动画阶段的通关路线，以及故意后插入障碍/危险区时最终校验确实拒绝地图。

### 墓室横向入口的补充约束

继续运行原提交的墓室回归时，seed 1 暴露出同一类问题的横向版本：一个后置棺椁占用了 `(832,128)` 附近的墓室横向地面。原提交仅预留纵向 `safeLane`，横向连接的中心延伸段尚未进入布局约束。现在有东西连接的墓室额外声明 `approachLanes`，散装装饰必须避让完整视觉区域，最终校验也检查该横向通道的可站立核心。

同时修正一处测试取点错误：旧用例只要墓室有任意水平连接，就同时检查东西两侧距边界 16px 的位置；其中未连接的一侧可能直接面向水域或地图外墙，无法容纳半径 26px 的 Boss。新用例逐条检查实际存在的连接口，仍保留横向墓道 `y-16 / y / y+16` 的真实碰撞回归，没有把合法入口处的失败排除掉。

本轮验证结果：墓室/主题密度 5 项回归与其余地图相关 40 项回归全部通过，其中主题安全通路覆盖 400 个种子 × 3 层，墓室真实连接和横向可走区域各覆盖 400 个种子。前端生产构建通过；浏览器场景能显示水波、完整火焰雕像和错峰地刺，控制台未发现错误或警告。

### 红框反馈：火焰雕像两侧与前方空地无法进入

第一次修复正确发现了 `Statue_fire.png` 5×5 组合的视觉 footprint 不能直接拿来做碰撞：原来的底行中间三格（局部 x=16、y=64、48×16）明显过宽。逐像素核对后，把真正的石质落地点收窄为局部 x=34..46、y=70..75，即 13×6；完整 80×80 图案和动画保持不变。这一步修正了“碰撞形状”，但实机反馈证明它**没有完整解决可进入性问题**。

#### 第二次追踪到的真正遗漏

第一版 `dungeon3-statue-collision.test.js` 只构造了一个没有水域、墙体、高差和后置布局的假房间，因此只能证明 13×6 碰撞框本身没有覆盖透明像素，无法证明它放进真实生成地图后仍有足够通行净空。真实 `generateDungeonGeometry()` 回归首先在 `seed 1 / floor 1` 复现：固定取样点 `(688,352)` 会撞到高台 `elevation`，说明必须区分“合法地形边缘”与“雕像造成的堵塞”，不能继续靠几个人工坐标判断。

继续按真实玩家半径 18 计算后，问题落在**雕像位置与碰撞半径的组合**：雕像原先只距房间西边 16px，13×6 的石质底座位于约 `room.x + 50..62`；玩家圆形半径会把其有效阻挡范围向左扩到约 `room.x + 32`，而西侧水岸又要求玩家中心至少离房间边缘约 18px。因此两者之间理论可走的玩家中心通道只剩约 14px。旧测试恰好走 `room.x + 28`，能命中这条数学上存在的细缝，于是测试通过；但 14px 对连续摇杆移动几乎没有实际容错，所以画面看起来是大片空地，玩家却很难甚至无法进入。

#### 最终处置

不再继续缩 13×6 的实体底座，因为它已经有原图像素证据；也不降低玩家半径，因为那会改变全局战斗碰撞。改为把完整 5×5 火焰雕像从 `room.x + 16` 整体向房间内部移动两格，到 `room.x + 48`。这样保留同一张 80×80 资源、同一 13×6 石质底座和中央祭坛通路，同时在西侧给半径 18 的玩家留下至少两列相邻的 16px 玩家中心通道，不再依赖单点细缝。

回归测试也改为两层：第一层继续验证素材局部碰撞——透明前景可穿过、石质底座仍阻挡、完整组合仍为 80×80；第二层直接用真实 `generateDungeonGeometry()`、真实水域/高差/墙体和玩家半径 18，跨 80 个 seed × 3 层检查雕像西侧两列实际通行点及前方可站立区域能否连回 shrine 中心。新回归在修复前明确失败于 `seed 1 / floor 1` 的 `(696,313)`，修复后通过。这里验证的是“实际可操控净空”，而不是“几何上存在一条无限窄的理论路径”。
