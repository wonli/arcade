# Endless Dungeon Combat Prototype Design

## Goal

Validate one question before building the persistent RPG: **is the first minute of combat fun enough to justify the rest of the game?**

This prototype is intentionally local-first. It does not add persistence, inventory databases, endless-floor generation, multiplayer, or server-authoritative combat yet.

## Product slice

Add **Endless Dungeon** as a new Arcade game entry and render the game world with Phaser inside the existing SvelteKit application.

The prototype contains:

- one dungeon arena
- one player character
- WASD movement
- automatic attacks against the nearest enemy in range
- one active skill on Space
- a stream of simple enemies, initially centered on Slime-style melee enemies
- health and combat death/restart
- hit flash, slash/projectile feedback, knockback, floating damage numbers, death particles and small screen shake
- loot drops with rarity presentation
- at least one visible equipment upgrade that immediately improves combat output

The success criterion is qualitative: within roughly 30 seconds the player should move, kill enemies, see satisfying hit/death feedback, receive loot, equip/pick up an upgrade, and feel an obvious increase in power.

## Technology boundary

Keep the existing Arcade architecture. Phaser is embedded only for the real-time game world.

- **SvelteKit** owns navigation, game selection, future inventory/settings/i18n UI, and the surrounding Arcade shell.
- **Phaser** owns sprites, camera, input, movement, enemy simulation, collisions, animation, particles and combat effects.
- **AQI/Go** is not part of prototype combat simulation. It remains the future authority for persistence, validated loot/progression, runs, leaderboards and multiplayer.

Do not introduce Unity, Godot, Matter.js, ECS, a navigation-mesh system, or a second frontend application.

## Assets

Use free assets first. Prefer CC0 assets with explicit source/license records in the repository.

Primary candidates:

- Debts in the Depths asset pack for dungeon creatures/environment where its visual set fits.
- Kenney Tiny Dungeon / Roguelike assets for gaps such as tiles, items or UI-adjacent game art.

Do not silently mix arbitrary packs. Keep a small `THIRD_PARTY_ASSETS.md` (or equivalent) recording source URL, author/package, license and which files were imported. Only commit assets whose license permits redistribution.

Combat presentation generated by the game should provide much of the identity: hit flashes, damage numbers, slash effects, particles, loot beams, shadows and camera feedback.

## Internationalization boundary

The prototype establishes the future-safe content boundary even though it only needs a small amount of text.

Game/content data uses semantic IDs rather than localized strings, for example:

- `monster.slime`
- `weapon.rusty_sword`
- `rarity.rare`
- `stat.damage`

The Svelte UI translates IDs. Runtime/content definitions never make Chinese or English names part of game identity. Start with Simplified Chinese and English language resources, structured so `zh-TW`, `ja`, `ko`, etc. can be added without changing game logic.

Numbers and icons should carry high-frequency combat information where practical.

## Prototype combat model

The player moves with WASD. The game continuously selects the nearest valid enemy inside attack range and attacks according to attack speed. This avoids requiring an aiming/action system before combat feel is proven.

Space activates one cooldown-based skill with strong visual feedback. The exact skill may be a radial slash or shockwave; implementation should choose the smallest option that clearly demonstrates active combat input.

Enemies use simple seek/chase behavior. No pathfinding is required in the first arena. Collision can use Phaser's simple built-in facilities or straightforward distance/AABB checks.

Combat stats stay deliberately small:

- HP
- Damage
- Attack Speed
- Crit Chance

The prototype may use deterministic/local random rolls where convenient; anti-cheat is explicitly out of scope until combat moves server-side.

## Loot loop

Enemy death can roll a ground item. The first implementation needs only enough templates/rarities to demonstrate the loop, not a complete item system.

A dropped item should have strong presentation: pop/bounce from the enemy, rarity color/light/beam, label, and pickup feedback. Picking up/equipping an upgrade should immediately affect player stats.

At minimum demonstrate common/uncommon/rare presentation. Higher rarities can be visual constants without a full loot table.

No permanent inventory is stored in this prototype.

## Runtime lifecycle

The Phaser game instance must mount and destroy cleanly with the Svelte component. Returning to the Arcade landing page must not leave timers, keyboard handlers, audio nodes, animation frames, or Phaser scenes running.

Resize behavior must preserve a playable viewport. The game should be keyboard-first on desktop; mobile controls are out of scope for the prototype.

## What is explicitly deferred

Do not build these until combat feel is approved:

- SQLite / player profiles / saved items
- persistent runs or checkpoints
- procedural infinite floors
- bosses and biome progression
- multiplayer/co-op
- server-authoritative movement/combat
- full inventory/equipment screen
- affix generation
- skill trees/classes
- leaderboards
- content authoring tools

## Verification

Automated checks should cover pure combat/content helpers where practical and, most importantly, verify that the existing frontend builds with Phaser integrated. Existing Arcade tests must remain green.

Manual acceptance pass:

1. Open Endless Dungeon from the Arcade landing page.
2. Move with WASD.
3. Observe automatic attacks against nearby enemies.
4. Observe visible hit feedback, damage numbers, knockback and enemy death effects.
5. Use Space and see a distinct active-skill effect/cooldown.
6. Kill enemies until loot drops.
7. Pick up an upgrade and observe a clear combat/stat improvement.
8. Leave the game and confirm the Phaser runtime is destroyed cleanly.
9. Switch between Simplified Chinese and English UI strings without changing content IDs.

Only after this prototype feels good should the project design the persistent Endless Dungeon runtime (`players`, `runs`, `items`) and procedural floor system.
